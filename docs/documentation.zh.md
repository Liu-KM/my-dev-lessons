# 文档维护规范

[English](documentation.md) | 中文

本页维护文档职责、lesson 写作要求与文档检查说明。按任务选择规范的入口是[贡献指南](../CONTRIBUTING.zh.md#按任务查找规范)。

## 规则归属

一条规则只有一个主要维护位置；已有中英文配对共同构成一个逻辑来源。其他页面可以保留必要的简短提示，但通过链接引用完整要求，不单独增加例外。

| 内容 | 维护位置 | 其他位置的职责 |
| --- | --- | --- |
| 项目目标与范围 | [MVP](../MVP.md) | README 介绍项目并提供入口 |
| lesson 写作与文档职责 | 本页 | 模板提供填写结构，贡献指南提供任务导航 |
| 双语配对、同步确认与记录 | [双语维护](bilingual-maintenance.zh.md) | 写作入口与模板链接该流程 |
| 概念、译名及保留原名的术语 | [术语表](../TERMINOLOGY.md) | 其他文档使用约定，不复制词表 |
| Issue、提交、PR 与合入 | [PR 协作规范](pull-requests.zh.md) | 贡献指南串联操作，Agent 指令提供提醒 |
| Agent 开始工作与讨论约定 | [AGENTS.md](../AGENTS.md) | CLAUDE.md 链接同一文件 |
| 工程经验与历史证据 | [lessons](../README.md#开发经验) | 解释为什么和适用条件；本项目操作链接对应规范 |

模板与检查器是规则的使用方。修改规则时核对它们是否需要同步调整；实现差异需要修复或明确讨论，不能把两套要求同时当作现行规范。讨论草稿与本地操作记录不是现行规则的来源。

## 学习与采用

对已经选定的 DSH 学习主题，默认沿用案例中解决该问题的职责、执行流程与检查机制。先核对具体版本和来源，再决定如何接入本项目；不把无关的 DSH 功能一并纳入范围。

提出差异的一方负责说明：原机制防止什么问题，该问题在本项目是否存在，哪个可核查的约束需要调整，以及调整后如何保留并验证原有保护。语言、运行环境或用户明确选择可以构成依据；“项目小”“保持简单”以及某项检查不能解决另一类问题，单独不足以支持省略机制。审阅者必须判断依据是否充分，不能只确认差异已经写出来。尚未补齐的机制标为缺口，不写成已接受的取舍。

## Lesson 写作

使用[中文模板](../templates/lesson.zh.md)或[英文模板](../templates/lesson.md)，保存到 `lessons/`。替换所有 `{{…}}` 占位符，并按[双语维护](bilingual-maintenance.zh.md)补齐另一语言、切换链接与记录。

- 标题直接说明问题或应用场景。
- 正文使用“问题 → 经验 → 方法 → 案例”四个非空二级章节及对应英文结构，细分用三级标题。问题讲通用机制，可辅以短例；经验给出可迁移判断，案例提供依据。
- 方法讲清“需求 → 缺口 → 解决 → 验证”的因果关系，写明职责、动作与结果；保留影响应用的条件与限制。
- 区分 DSH 实际做法、我们的推断和本项目采用方式。成功设计与失败修复都可作案例，有效性以案例证据判断。
- 案例链接具体提交，标签写明提交与改动主题；结合该版本的代码、测试或决策记录说明依据，不补造动机。
- 案例写清支撑结论的观察或结果，区分源码阅读与实际运行。复跑细节链接示例说明或已有证据，本次检查与 CI 结果放 PR；不强制“验证状态”字段。未执行的操作不能写成已通过。

## 修改规则

先按上表找到维护位置，再搜索规则的独特措辞、相关概念及指向它的链接，检查是否存在副本或冲突。更新主要维护位置及其已有译文；按影响调整模板、检查器和使用该规则的内容。入口只负责导航，不重复完整条款。

引用仓库内规范时使用指向文件或章节的相对 Markdown 链接，方便读者跳转和链接检查。移动规则时同时修正入站链接；旧位置可以保留指向新位置的入口。

审阅时从 README、贡献指南或 Agent 指令走一次实际任务路径，确认能找到更新后的规则；再检查旧位置没有留下相互独立的完整定义。链接可解析不等于规则位置正确，重复语义与例外仍需人工审阅。

## 新增与整合内容

新增或审阅 lesson、项目规则前，作者先按规则归属和任务导航读取相关内容，再搜索主题、相关概念及独特措辞。比较要解决的问题、适用条件、结论和证据；相似措辞只是线索，不代表内容重复。

| 比较结果 | 处理方式 |
| --- | --- |
| 相同条件和结论，只增加案例 | 将有用证据补充到已有 lesson，不另建同义条目 |
| 同一问题增加条件、例外或解释 | 补充已有内容，保留成立条件 |
| 不同场景得出不同结论 | 明确场景差异，保留必要区别并相互引用 |
| 相同条件下结论相互冲突 | 核对证据，明确修正或替代关系；未决结论不写成现行要求 |
| 独立问题且存在可复用的新判断 | 新增 lesson，说明它与相关内容的区别 |
| 普通修改过程，没有新的长期判断 | 使用 PR 描述或已有操作文档，不为填模板新建 lesson |

lesson 不自动成为强制规则。采用为项目规则时，说明本项目的具体需要、适用范围、执行者、检查或审阅方式，并修改已有规范的主要维护位置。lesson 保留经验与证据，通过链接指向本项目要求。

整合或替代时，保留仍有用的独有理由、例外、取舍及验证缺口；部分替代不能删除仍然成立的内容。完成整合后才删除多余副本，并同步译文、配对记录及入站链接。历史案例继续描述当时的事实，不因现行规则变化而改写为相反结论。

作者在 PR 的变化说明中链接相关内容并简述此次取舍；审阅者核对比较是否充分、条件是否丢失，以及是否把经验误当成通用要求。Agent 协作与用户审阅按[提交前协作审阅](pull-requests.zh.md#提交前协作审阅)执行。机械检查通过不能证明没有语义重复或冲突。

内容审阅与下述篇幅检查共同约束增长；不能用删掉必要条件来满足长度指标。原理与案例见[新增经验与规则的取舍](../lessons/lesson-and-rule-decisions.zh.md)。

## 篇幅约束

[清单](../scripts/doc-budgets.manifest.json)限定常驻入口和操作规范：[检查器](../scripts/check_doc_budgets.py)只读检查每个条目的文件、计量方式与上限。文件缺失、条目无效或超限时失败，清单外文件不设上限。迁移或删除受限文件时同步修改清单，审阅者确认其保护没有被无意移除。

| 范围或参数 | 选择依据 |
| --- | --- |
| 根目录 Agent 指令、README、贡献指南、文档维护、PR 协作、双语维护规范 | 这些常驻入口和操作规则会随任务持续追加；已有双语页面两侧都受限 |
| lessons、术语表、模板及 MVP 草稿不在清单中 | 分别承载历史案例、参考条目、填写结构和待定需求，不用统一的入口篇幅约束代替内容审阅；CLAUDE.md 是已有指令的链接，不重复计数 |
| `words` | 英文沿用 DSH 的空白分词计数，覆盖整个文件，包括代码和 Markdown 标记 |
| `characters` | 中文文件按非空白 Unicode 字符计数，英文片段和标记也计入；这是稳定的长度指标，不是中文分词或模型 token 数 |
| `max` | 本轮采用审阅后大小加至少 5% 余量的固定初始上限，向上取整；具体数值只在清单维护，不随文件增长自动刷新 |

编辑或审阅时发现重复、过时内容或职责混杂，即可按需整理，不必等到超限；没有具体问题就保持原样。不设定期整理、压缩比例或必须产出的要求。先按归属迁移并留链接，再精简冗余，保留必要条件。

整理明显改变篇幅后，在同一 PR 中审阅是否下调上限，保留至少 5% 余量；零星措辞修改无需重设。确需提高上限时，说明内容为何属于本页、为何不能迁移或精简及新值依据；计量或范围变更同样需要说明。由审阅者核对、用户审阅后再提交。检查器不自动改上限，也不判断是否需要整理。

`python scripts/check_doc_budgets.py --list` 显示用量及条目错误，沿用 DSH 的观察模式：即使超限或条目缺失也返回成功，不能用于 CI 强制检查；清单本身无法读取或解析仍失败。强制检查必须使用不带 `--list` 的入口。

沿用 DSH 的固定清单、失败检查及调整审阅；Python 复用已有环境。篇幅合格不证明无重复或冲突，上限也不是越低越好的目标。

## 文档检查

在仓库根目录运行 Python 文档检查（Python 3.9 及以上，无第三方依赖）：

<!-- doc-check-entry -->
```sh
python scripts/check_docs.py
```
<!-- /doc-check-entry -->

[统一入口](../scripts/check_docs.py)运行连接、结构、配对、篇幅检查及回归测试，失败即退出。[连接检查](../scripts/check_doc_entry.py)核对本页命令块、CI 步骤及 hook；范围与实验见[案例](../lessons/documentation-check-entry.zh.md)。

用 `git config --get core.hooksPath` 查看已有 hook；有则先整合，无则用 `git config core.hooksPath .githooks` 启用[推送前检查](../.githooks/pre-push)。

[工作流](../.github/workflows/docs.yml)在 push、PR 和手动触发时运行上述检查、Markdown 基础格式及本地文件链接和标题锚点检查。[格式配置](../.markdownlint-cli2.jsonc)排除参考克隆和链接到 AGENTS.md 的 CLAUDE.md；链接检查离线执行，不验证外部网址。

lesson 结构检查验证标题、固定章节、案例来源链接及模板占位符；双语检查的范围与限制由[双语维护](bilingual-maintenance.zh.md#检查范围)说明。当前检查不能证明来源支持结论、翻译语义正确或命令能执行，也不执行文档示例类型检查或部署网站。第一条经验的[案例](../lessons/docs-example-typecheck.zh.md#案例)同时作为结构与中文锚点检查样本。

远程检查是否成功以对应提交的 Actions 记录为准；必要检查与合入约束见 [PR 协作规范](pull-requests.zh.md#自动检查与启用)。
