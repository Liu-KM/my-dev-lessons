# 将可替换实现与公共流程分开

[English](module-responsibilities.md) | 中文

## 问题

一段代码同时负责公共流程和某一种具体实现时，更换算法、存储后端或模型供应商，就可能牵动校验、错误处理和结果组织。复制整套代码绕过修改，又会产生多份需要同步的公共逻辑。

这是职责混杂带来的耦合：本应独立变化的部分，被迫一起修改。功能逐个增加，改动的影响范围也随之扩大。

例如，同样格式的数据从本地文件改为对象存储读取时，如果读取、解析和统计写在同一个函数里，就很难只替换读取方式。

## 经验

**按变化原因划分职责，把可替换的实现与需要保持一致的流程分开。** 实现决定具体怎样完成工作，调用方通过共同约定使用它。这样，替换实现和调整公共流程各有明确的修改位置。

这里的接口是双方共同遵守的输入、输出和错误行为约定，可以由函数或类型表达。这是关注点分离的一种应用，适用于同一项能力需要不同实现的场景。

## 方法

从一次实际变更出发，区分哪些代码随实现变化，哪些要求需要共同维护：

| 部分 | 负责什么 |
| --- | --- |
| 接口 | 定义调用方需要的输入、输出和错误行为 |
| 实现 | 完成具体计算、存储或外部服务调用 |
| 调用方 | 组织任务流程，通过接口使用实现 |

根据实际替换需求决定拆分位置。用两种改动检验划分：替换实现时，调用方仍按同一约定工作；修改公共要求时，所有实现通过同一入口采用更新。新实现暴露了约定缺失，就一起更新接口、调用方和测试。

## 案例

[DSH 提交 8b5a3ef730：拆分 Bash 接口、实现和工具调用](https://github.com/deepseek-ai/deepseek-harness/commit/8b5a3ef7300e5b100c66268f9c761c660172b298)将执行约定、本地进程操作和模型工具分开。工具依赖执行接口，本地执行器实现该接口；拆分依据是各部分需要独立替换。

[DSH 提交 ab19fed77c：接入两个 LLM 适配器并补齐错误处理](https://github.com/deepseek-ai/deepseek-harness/commit/ab19fed77c4b744f4447d72de0dfd59dca7c82a3)在接入实现时，也更新了核心对流内错误的处理及测试，补齐共同约定。

本项目的[attention 示例](../examples/module-responsibilities/README.zh.md)用函数参数替换计算实现，用 Python 模块维护公共流程：`run_attention`负责校验、计时和输出检查，两个计算函数负责各自的算法。公共校验增加“拒绝 NaN”后，两种算法均在执行前被拦住，计算函数保持原样；计算结果另与独立参考值核对。attention 是这条通用方法的验证案例。

验证状态：DSH 证据来自历史源码与测试阅读。本项目在 Python 3.9.7 / NumPy 2.0.0 下通过八项 CPU 案例测试。
