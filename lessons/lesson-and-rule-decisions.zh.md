# 新增经验与规则的取舍

[English](lesson-and-rule-decisions.md) | 中文

## 问题

每次改动都追加一条经验或规则，会让相同结论反复出现，旧结论和新例外也可能同时被当作现行要求。已有主要维护位置只能说明内容放在哪里，不能判断它是否值得增加。

为了减少篇幅直接合并或删除同样有风险：相似表述可能适用于不同场景，旧记录中仍有用的理由和尚未验证的部分可能被一并删掉。

## 经验

新增内容应增加可复用的判断或必要证据。先比较它与已有内容的问题、条件和结论，再决定补充、新增、合并或替代。经验成为项目规则还需要具体的应用需求和执行方式。

自动检查可以发现章节缺失或文档超长；内容是否必要、规则是否冲突、合并时是否丢失适用条件，则需要人或 Agent 审阅。篇幅合格不代表内容正确。

## 方法

从相关内容的主要维护位置开始比较。同一结论的新案例通常补充已有证据；独立问题才可能需要新条目；条件不同的结论保留区别；同条件冲突先核对来源，明确修正或替代关系。位置与导航的方法见[规则集中维护与查找](rule-ownership-and-discovery.zh.md)。

把比较放进实际改动与审阅：作者链接相关内容并解释取舍，审阅者检查必要性和条件是否保留。合并时保留仍有用的理由、取舍和尚未验证的部分，同时修正引用；不能假定 Git 历史可以替代读者需要的现行说明。

对经常追加内容的入口文档，可以检查指定文件的长度，超限时要求重新审阅。先判断新增内容是否应放在别处，再精简；仍需提高上限时说明理由。上限、计量方式和修改理由也需要审阅；修改配置后检查通过，不证明新上限合理。按空白分词的英文计数不能直接代表中文篇幅。

本项目的执行步骤与职责由[新增与整合内容](../docs/documentation.zh.md#新增与整合内容)维护；本 lesson 解释经验，不另设一份项目规则。

## 案例

[DSH 提交 `aa36b3b36b`：为常驻文档增加职责划分和篇幅检查](https://github.com/deepseek-ai/deepseek-harness/commit/aa36b3b36bcb46ef3c9d37b23c3145439fd7bf1a)

- **问题**：提交记录指出，根目录指令在两周半、50 次提交后达到 8,130 个词；已有写作规则未阻止相同要求和事故说明反复追加。
- **办法**：明确各类内容由哪份文档维护，并用清单设置少数易增长文件的篇幅上限。检查接入文档检查和 CI，超限或清单中的文件缺失会失败；它不能判断规则是否互相矛盾。
- **证据**：[决策记录](https://github.com/deepseek-ai/deepseek-harness/blob/aa36b3b36bcb46ef3c9d37b23c3145439fd7bf1a/docs/rfc/implemented/process/2026-07-04-doc-tiers-and-budgets.md)和[检查器](https://github.com/deepseek-ai/deepseek-harness/blob/aa36b3b36bcb46ef3c9d37b23c3145439fd7bf1a/scripts/verify-doc-budgets.ts)。

后续[提交 `c60eb87860`](https://github.com/deepseek-ai/deepseek-harness/commit/c60eb878601f54ee5a9d32496c7e2237a49643b0)明确了超限后的处理顺序：迁移、精简，最后才是说明理由并提高上限；同时保留至少 5% 的工作余量。这与最初按当前大小冻结上限的方案有所演进。

[DSH 提交 `3feb05fef8`：整合完全被替代的决策记录](https://github.com/deepseek-ai/deepseek-harness/commit/3feb05fef83a956e73b0a28057c8cd13bebf3dfd)

- **办法**：允许整合完全被替代的记录，但要求保留独有理由、备选方案、后果和尚未验证的部分，并修复引用；部分替代仍保留两份记录及其关系。具体要求由[该版本的记录规范](https://github.com/deepseek-ai/deepseek-harness/blob/3feb05fef83a956e73b0a28057c8cd13bebf3dfd/.agents/notes/README.md#when-to-write-one)维护，不由词数检查判断。

[DSH 提交 `730bcc7c85`：以长期决策价值作为记录条件](https://github.com/deepseek-ai/deepseek-harness/commit/730bcc7c856141e09566c35c835b1109dd6c90a6)

- **办法**：将“每个非平凡改动都要记录”改为只记录现有代码、测试和文档未解释的长期维护理由；同一决策补充原记录，普通改动留在 PR 或已有文档中。该提交还明确不能为填模板编造备选方案。这是 DSH 对决策记录的要求，将其用于 lesson 的新增判断是本项目的应用。

本项目逐项比较了以下内容；表中结论来自审阅，不是检查器自动给出的判断：

| 比较样本 | 判断与处理 |
| --- | --- |
| 本案例的归属、导航和篇幅检查，与已有“规则集中维护与查找” | 已有经验覆盖这些机制，方法部分引用原 lesson；本篇保留解释新增与替代判断所需的案例背景 |
| 本篇的新增条件与旧 lesson 的维护位置 | 两者互补，保留独立主题；项目操作只在文档规范增加一个维护位置 |
| “文档代码示例类型检查”与“双语文档一致性维护” | 都验证文档，但前者验证代码类型，后者验证结构、原样代码与同步记录，不能合并成“检查通过即可证明文档正确” |
| 假设新增“检查通过即可自动合入”，与现行用户确认要求 | 同一合入场景下冲突；未采用该假设要求，继续由 PR 协作规范维护合入条件 |

本项目也按 DSH 的做法设置文档篇幅上限：[文件清单](../scripts/doc-budgets.manifest.json)维护固定上限，[检查器](../scripts/check_doc_budgets.py)通过 `python scripts/check_doc_budgets.py` 执行，并接入[文档 CI](../.github/workflows/docs.yml)。初始清单覆盖 10 个常驻入口和操作规范文件；规则是否冲突仍由审阅者判断。

实现使用已有的 Python 检查环境，英文按空白字符分词计数，中文统计非空白字符，避免整段中文被当作一个词。文件范围、至少 5% 余量和调整顺序见[篇幅约束](../docs/documentation.zh.md#篇幅约束)。语言和计数方式虽有调整，仍保留固定清单、超限或缺文件时失败、上限调整须经审阅的要求；没有因项目规模小或无法自动判断规则冲突而省略篇幅检查。

实验在临时清单中将一个示例文件的上限设为 10 个词，运行未经修改的 DSH `ce7073d512` 检查器。普通短文通过；11 个词和文件缺失分别以退出码 1 失败；包含“始终要求审阅”与“从不要求审阅”的英文短文仍通过。这些样本用于确认篇幅检查能发现什么、会遗漏什么，不是 DSH 曾发生的事故。

验证状态：已核对上述历史提交，以及本地 DSH `ce7073d512` 的规范、Skill、检查器和 CI 调用关系。使用 Node 24.22.1 直接运行篇幅检查器，7 个受限文件通过；临时文件实验验证了上述四种结果。未运行完整 DSH 文档检查或其远程 CI，也未测量长期能否减少重复或冲突。本项目完成了表中的手工比较，并实现篇幅检查及通过命令行运行检查器的回归测试；本次改动的实际检查结果和远程 CI 状态由 PR 验证说明提供。这些人工比较不能证明审阅能识别所有冲突。
